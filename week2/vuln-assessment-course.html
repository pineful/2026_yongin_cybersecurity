Pre-requisites · 업무 필수 수칙

실무 취약점 진단 착수 전 필수 체크리스트 4가지

허가받지 않은 스캔은 정보통신망법 위반(해킹)입니다. 반드시 사전에 확인해야 할 4대 원칙
법적 권한 및 진단 범위 (Legal & Scope)
1 사전 서면 승인 (Written Consent)
고객사 CISO 또는 인프라 부서의 공식 서면 동의서 없이 수행하는 모든 스캐닝 행위는 형사 처벌 대상입니다.
위반 시 5년 이하 징역 또는 5천만 원 이하 벌금 서면 문서 날인 필수
2 대상 IP 대역 범위 확정 (Scope Lock)
승인되지 않은 제3자 시스템이나 클라우드 공유 인프라를 실수로 스캔하지 않도록 정확한 IP 목록을 확정합니다.
AWS/공유 인프라 오인 스캔 시 영업방해 손배 정확한 IP 사전 고정
데이터 안전성 및 운영 연속성 (Safety & Continuity)
3 사전 데이터 및 설정 백업 (Data Backup)
자동 스캐너의 고속 패킷이나 익스플로잇 테스트로 인해 서비스 데몬 크래시 또는 데이터 손상이 발생할 수 있습니다.
무중단 DB 덤프 및 VM 스냅샷 백업 사전 스냅샷 완료 확인
4 업무 외 시간대 수행 (Service Hours)
주간 트래픽 피크 타임 스캔 시 네트워크 과부하로 정상 고객 서비스 장애가 유발되므로 야간·주말에 진행합니다.
야간(22:00~06:00) 또는 정기 점검 시간대 비상 연락망 상시 대기

Core Methodology · 서비스 식별

포트 스캔과 서비스 식별의 원리: 배너 그래빙(Banner Grabbing)

단순히 문이 열렸는지 확인하는 것을 넘어, 문 뒤에 서 있는 소프트웨어의 이름과 버전을 알아내는 기술
💡 용어 돋보기 배너 그래빙 (Banner Grabbing) = 서버 연결 직후 자동으로 회신되는 환영 메시지(소프트웨어 이름·버전)를 낚아채 취약점을 식별하는 기법

1. 왜 서비스 식별이 핵심인가?

"21번 포트가 열려 있다"는 사실만으로는 공격하거나 방어할 수 없습니다.

  • 열린 문 뒤의 프로그램이 vsftpd 2.3.4인지 최신인지 알아야 취약점 여부를 판별합니다.
  • 버전이 식별되는 순간, 공격자는 공개 CVE 데이터베이스에서 무기화 코드를 즉시 탐색합니다.
진단자의 핵심 원칙: "포트 개방은 출발점일 뿐, 최종 목표는 서비스 식별과 CVE 매핑이다."

Tool Mastery · Nmap

Nmap 핵심 옵션 비교: 실무에서 가장 많이 쓰는 5대 스위치

네트워크 보안 진단 도구의 사실상 표준 Nmap의 필수 옵션과 동작 메커니즘
포트 스캔 & 서비스 식별 옵션
-sS (SYN 스텔스 스캔) nmap -sS <IP>
TCP 3-Way Handshake를 완성하지 않고 SYN-ACK 직후 RST를 전송하여 서버 로그를 최소화하는 고속 스캔의 정석.
-sV (서비스 버전 감지) 오늘 핵심 실습
단순 포트 개방 여부를 넘어 데몬과 직접 핸드셰이크하여 소프트웨어 이름과 정밀 버전(배너)을 식별.
-p- (전체 65,535개 포트 스캔) nmap -p- <IP>
기본 1,000개 대표 포트 점검을 넘어 비표준 포트(8080, 8443, 6200 백도어 등)에 숨겨진 취약 서비스를 전수 발견.
스크립트 엔진 & 템포 제어
-sC (기본 스크립트 실행) nmap -sC <IP>
Nmap Scripting Engine(NSE) 기본 스크립트를 자동 구동하여 익명 FTP, SSL 인증서 정보, 취약점 서명을 자동 진단.
-T4 (공격적 템포 가속) 신뢰 네트워크 표준
패킷 전송 간격과 대기 시간을 지능적으로 단축하여 스캔 속도를 대폭 끌어올림 (안정적인 사내망 실습 권장값).
💡 실무 표준 1-Line 조합 명령어
nmap -sS -sV -p- -T4 <Target_IP>

Methodology · 진단 관점 비교

외부 진단 vs 내부 진단: 공격자의 시선에 따른 차이

인터넷 경계 방화벽 외부에서 진입로를 찾는가, 이미 사내망에 침투한 내부자의 시선인가

🌐 외부 진단 (Black-Box Testing)

인터넷에 공용 IP로 노출된 대외 웹 서버를 대상으로 진단합니다.

  • 노출 자산: 80(HTTP), 443(HTTPS) 중심 대외 웹 서비스
  • 평가 목적: 웹 취약점을 통한 최초 침투(Initial Access) 가능성 검증
  • 특징: 방화벽과 IPS에 의해 비인가 포트가 엄격히 사전 차단됨

🏢 내부 진단 (White/Gray-Box)

방화벽 안쪽 사내 LAN 망에 이미 접속한 공격자 관점의 진단입니다.

  • 노출 자산: FTP(21), NFS(2049), DB(3306), SMB(445) 사내 서비스
  • 평가 목적: 횡단 이동(Lateral Movement) 및 핵심 기밀 탈취 경로 점검
  • 특징: 사내망에 무방비로 열린 레거시 취약 서비스 집중 탐지 (실습 무대!)

FTP Architecture · 이원화 통신 구조

FTP의 특이한 구조: 명령 제어선(21)과 데이터선(20)

하나의 연결로 다 처리하는 웹(HTTP)과 달리, FTP는 명령을 내리는 줄과 파일을 나르는 줄이 분리되어 있습니다.

1. 제어 연결 (Control - 21번 포트)

세션이 유지되는 동안 계속 열려 있는 지휘 통제선.

  • 역할: 로그인 인증(USER/PASS), 경로 이동(CWD), 파일 조회(LIST) 명령 송수신
  • 특징: 경량 텍스트 제어 명령만 전달되며 실제 파일 본문은 전송되지 않음

2. 데이터 연결 (Data - 20번 또는 동적 포트)

파일 전송 시에만 잠깐 열렸다가 전송 후 즉시 닫히는 수송선.

Mode Comparison · 능동 vs 수동

FTP 능동(Active) 모드 vs 수동(Passive) 모드

서버가 클라이언트에게 찾아오는 능동 모드는 방화벽에 막힙니다. 그래서 수동 모드가 탄생했습니다.

🚚 능동 모드 (Active Mode - PORT)

클라이언트가 임의 포트를 열고 서버에게 "여기로 배달 와라" 요청.

  • 서버(20번)가 클라이언트 임의 포트로 인바운드 역접속 시도
  • 방화벽 차단: 클라이언트 공유기·방화벽이 외부 역접속을 침입으로 차단
  • 실무 증상: 로그인은 성공하나 LIST 파일 목록 조회에서 무한 대기

🛒 수동 모드 (Passive Mode - PASV)

서버가 데이터 포트를 열고 "이 번호로 데이터 가지러 와라" 안내.

  • 클라이언트가 서버 고포트(예: 50000번 대)로 직접 아웃바운드 접속
  • 표준 채택: 클라이언트 방화벽 인바운드를 거스르지 않아 오늘날 표준
  • 실무 해결: 파일 전송이 멈추면 즉시 PASV 수동 모드로 전환

NFS Architecture · 포트 및 RPC 원리

NFS 아키텍처: 2049 포트와 RPC(111번) 안내데스크

NFS는 혼자 일하지 않습니다. rpcbind(111)와 mountd 데몬이 포트를 매핑해주는 원리를 이해합니다.

1. rpcbind (111번 포트) = 건물 안내데스크

NFS 보조 데몬들은 구동 시마다 포트 번호가 동적으로 변경됩니다.

  • 클라이언트 질의: 111번 rpcbind에 "mountd 현재 몇 번 포트인가요?" 문의
  • 동적 포트 안내: rpcbind가 현재 구동 중인 mountd 포트(예: 32771) 회신
  • 필수 사전 관문: rpcbind가 닫혀 있으면 클라이언트는 마운트 경로를 찾지 못함

2. nfsd & mountd = 실제 부서 사무실

안내데스크에서 포트를 확인한 클라이언트가 직접 서비스 창구로 접속합니다.

  • mountd (동적 포트): 인증 및 /etc/exports 기반 마운트 승인 처리
  • 고정 포트 2049: NFS 실제 파일 읽기·쓰기를 담당하는 표준 통신 창구
  • 진단 핵심: Nmap 스캔에서 111번과 2049번이 열려 있으면 ➔ NFS 진단 착수!
NFS 3단계 마운트 핸드셰이크 아키텍처 도식
rpcbind 안내 ➔ mountd 인증 ➔ nfsd 파일 I/O
1단계. 포트 번호 문의
Client ➔ Server [111/rpcbind]
"mountd 데몬 포트 번호 안내 요청"
➔
2단계. 마운트 권한 인증
Client ➔ Server [32771/mountd]
/etc/exports 대조 및 마운트 핸들 수령
➔
3단계. 원격 파일 I/O
Client ➔ Server [2049/nfsd]
사내 로컬 디스크처럼 원격 파일 입출력
Configuration · 설정 파일 분석

NFS의 심장: /etc/exports 설정 문법과 옵션

어떤 폴더를, 누구에게, 무슨 권한으로 열어줄 것인가를 결정하는 리눅스 핵심 설정 파일

📝 /etc/exports 기본 문법 구조

/etc/exports Syntax
[공유디렉터리] [허용할 대상 호스트]([옵션])
/data 192.168.10.50(ro,root_squash)
/var/log 192.168.10.0/24(rw,sync)

호스트 IP 지정과 괄호 사이에는 공백이 없어야 합니다.

⚙️ 주요 권한 제어 옵션

  • ro (Read-Only): 오직 읽기만 허용 (보안에 안전)
  • rw (Read-Write): 파일 쓰기 및 수정 허용
  • sync: 변경 사항을 실시간 디스크 동기화
  • root_squash: 원격 root를 nobody로 격하 (필수 방어 옵션!)
  • no_root_squash: 원격 root 권한을 그대로 인정 (치명적 백도어!)
Vulnerability Analysis · 3대 위험 옵션

NFS를 침투 구멍으로 만드는 3대 취약 설정

관리자의 무심한 한 줄 설정이 서버 최고 관리자 권한 탈취로 이어지는 3가지 실수

1. 전 세계 공개 (*)

호스트 미지정 와일드카드 개방.

  • 사내망 누구라도 자유롭게 원격 마운트 가능
  • 올바른 설정: 192.168.10.50 특정 단일 IP로만 제한

2. 루트 ( / ) 공유

최상위 루트 파일시스템 통째 공유.

  • /etc/shadow 및 시스템 핵심 바이너리 전면 노출
  • 올바른 설정: /shared/docs 전용 하위 폴더만 한정 공유

3. no_root_squash

원격 root 권한 그대로 인정.

  • 공격자가 원격에서 root 권한으로 SUID 파일 생성 가능
  • 올바른 설정: 기본값 root_squash로 nobody 강등 필수
/etc/exports 핵심 보안 설정 대비 및 위험도 매핑
위험한 설정(침투 통로) vs 안전한 표준 설정(방어)
❌ 치명적 취약 설정 (오늘 실습 타깃)
/ *(rw,no_root_squash,sync)

✅ 권장 안전 설정 (실무 표준)
/data/shared 192.168.10.50(ro,root_squash,sync)

Remediation · 보안 대책 총정리

NFS 보안 조치 3원칙: 설정·권한·네트워크

주요정보통신기반시설 취약점 가이드라인(U-21) 기준 완벽한 보안 조치 방안

1. 접근 IP 엄격 제한

와일드카드(*) 완전 제거 원칙.

  • 반드시 마운트가 필요한 단일 호스트 IP만 명시
  • 예: /backup 192.168.10.20(rw)

2. root_squash 필수 적용

원격 관리자 권한 nobody 박탈.

  • 원격 클라이언트가 root여도 nobody(65534)로 강등
  • 원격 SUID 파일 생성을 통한 권한 상승 차단

3. 경계 방화벽 차단

외부 인터넷 노출 차단선 구축.

  • 111(rpcbind)과 2049(NFS)의 대외 인터넷 유출 차단
  • 오직 승인된 사내 관리망 IP에서만 접속 허용

네트워크 ➔ 설정(호스트) ➔ 커널 권한 3단계 통제
1차 방어선: 네트워크 차단

/etc/exports 내 와일드카드(*) 금지 및 특정 서버 IP 지정

3차 방어선: root_squash

💥 폭발 반경 (Blast Radius)의 개념
